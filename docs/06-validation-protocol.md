# Validation protocol

Updated: 2026-10-11. [D-005](08-decisions-and-questions.md#d-005--validation-independent-of-burneum-2026-10-10) supersedes the initial Burneum proposal: the owner will not continue it. This protocol requires no other active project. Technical validation and a later value pilot have different purposes and evidence.

## Technical validation before the value pilot

The plugin-first direction remains accepted in [D-001](10-plugin-direction-and-technical-test.md). Choose one host and one documented, authorized source after the capability study. Prepare a small controlled task in a test workspace, for example changing a function and running its check. Record goal, host/version, task/session, tools/agents, expected action/result and source coverage. Test data may be artificial; the agent activity must genuinely execute. Label fixtures used to inject failures separately.

Before capture, record authorization for the specific session/source, included/excluded fields, redaction before storage or remote processing, retention/deletion, and revocation. A plugin installation or approval of a task script is not blanket authorization. Do not use secrets, personal data or client/employer material; another project's real data requires a new explicit data decision.

Execute: installation/trust → useful panel while work continues → observed action/result → contextual question → generated explanation with navigable source → node saved and marked → close application → recover node, mark and source after reopening. Record event IDs and sanitized evidence. If inter-agent messages cannot be observed, show the gap without reconstructing them. Check deactivation, capture failure, duplicate/lost events and redaction with fictional secrets.

Pass only when the full flow runs in the identified environment, preserves provenance and recovers the map. An animation demo, static import or mocked explanation alone does not prove live capture or the complete integration. Report capabilities, omissions and failures separately. If useful presence or authorized coverage is insufficient, apply D-001's review condition. Technical success does not establish user value or authorize launch.

## Preparing the value pilot

After the initial usable version is technically validated, choose a current real task or a controlled comparable exercise with the owner; no project is prescribed. Record goal, tools/agents, observable source, completion criteria and questions that are hard to answer today. Obtain separate permissions and privacy/retention decisions for new data or participants. Keep testing private; it is not public user acquisition.

Prepare two comparable runs, one with the usual workflow and another with Tramora, or at least a descriptive baseline of the usual workflow. Define concrete questions and correct-answer criteria before testing. Examples: "What decision was proposed or made?", "What source supports it?", "What remains unknown?", "Can I find the explanation days later?" Missing evidence is an acceptable answer when correctly declared. Agent proposal and human decision remain distinct.

## Value-pilot sequence

1. Connect the authorized session; importing can support memory evaluation but does not demonstrate live observation.
2. Identify a decision that raises a real technical question. Record time and correctness with the usual workflow and with Tramora, including an honest lack of evidence.
3. Open the short explanation, expand it with an example or detail, and navigate to the origin of important claims.
4. Try a suggested question and a free-form question. Verify that both stay in the decision's context.
5. Save and mark a map node. Close and return after 3–7 actual days; recover the node, explanation and source. Opening is not evidence of understanding.
6. Compare answers and recalled context with the source. Record confusion, distraction and excessive detail. Evaluate the full return view when it is available; do not attribute its effects to an unimplemented feature.

## What to measure and decide

- Time to a useful explanation and number of window/conversation switches.
- Correct answers about decision, source, alternative and limitations; distinguish confidence from accuracy.
- Important claims with navigable sources and correctly declared unknowns.
- Time to recover a marked concept after 3–7 days.
- Suggested questions used/ignored, nodes saved/revisited and comments on missing coverage or distraction.

Record actual results, sample limits and negative findings. If people understand just as quickly with the usual workflow or do not return to the map, revise the product before broadening integrations. Do not claim time savings or other benefits before measurement. A controlled exercise does not establish value across customer projects.

## Open publication (no commercial track)

Technical validation and value evidence do not make a commercial product, and Tramora is not one: it is **not sold** and is published as an open-source repository under **Apache-2.0** ([D-008](08-decisions-and-questions.md#d-008--open-publication-under-apache-20-no-commercial-track-2026-10-11)). The earlier plan for a commercial launch (access, test-mode purchase, verified webhooks, delivery/installation, operational email, customer texts, support) is **retired** and is not a requirement. What remains is ordinary open-source hygiene: the `LICENSE` file and a README stating the status and limits; publishing the repository, changing visibility or cutting a release requires the owner's explicit authorization. The truthfulness, privacy and authorized-capture rules are unchanged, and nothing here authorizes capture of real data (T0-04b).
