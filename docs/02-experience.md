# User experience

## Interface structure

The proposal has two main views and a contextual companion. The **Room** shows the current work and the exchanges between agents. **My map** keeps the path of questions, explanations, examples and decisions. The companion appears next to both views and explains the selected point. An internal standalone prototype demonstrates this structure with a fictional case.

### Agent room

Each visible agent has a stable identity, a role name, an assignment and an observed status. A given session might have a coordinator, a builder and a reviewer, but Tramora would not impose three agents or create characters that did not take part. Selecting an agent opens its latest relevant message, the artifacts it contributed to and the pending issues.

The communications thread uses directed relationships and precise verbs: "sent assignment" («envió encargo»), "proposed" («propuso»), "requested review" («pidió revisión»), "flagged a conflict" («señaló un conflicto»), "replied" («respondió») or "delivered result" («entregó resultado»). Each relationship points to an original message or event. A summary generated by Tramora is marked as an interpretation. If the integration only observes status changes, that change is shown without inventing a dialogue between agents.

Task status and agent status are different: a task may remain pending when no agent is running, or it may require human attention. This distinction prevents an avatar animation from conveying activity that does not exist.

### Animated room and synchronized log

The owner approved a second visual direction inspired by a [four-agent handoff example](https://x.com/jeetnirnejak/status/2086804226777420177): recognizable avatars that move and a log that fills in below. An internal demo materializes the idea with a fictional sequence. An agent that is working has a subtle movement and a text label; those that are waiting stay still. A small avatar crosses between two participants only during a handoff represented in the log. Animation and text are based on the same event.

The log shows relative time, type, sender, recipient when there is one, summary and detail/origin. The person can play, pause, step forward, restart or select an earlier row. That selection highlights the participants and opens the contextual explanation, without creating another event or pretending the agent worked again. "View origin" («Ver origen») distinguishes the observed data from the added explanation. Reduced-motion mode suppresses movement while keeping statuses and controls readable.

This is an approved interface direction, not an operational connection. In real sessions, movement and logs must come from actually observed events. If an integration does not expose the handoff or the message, the UI indicates the missing information instead of inventing it.

### Companion and anticipated questions

When it detects a relevant concept or decision, the companion proposes two or three concrete questions. Its candidates may cover the meaning, the practical consequence, an example, an alternative or an issue that is still unresolved. The person can also write a free-form question.

Not every technical word should trigger a suggestion. The priority would be to show one when it blocks a decision, affects the original goal, introduces a new rule or reappears in the session. It must not flood the work with continuous notices.

The depth of the answer is chosen independently of the person's technical level:

- **Brief:** core idea and immediate consequence, in plain language.
- **With example:** a small case from the project or an example declared as illustrative.
- **In depth:** assumptions, limits, alternatives and whatever remains undefined.

The answer includes "why it matters here" and a link to the message, document or artifact that prompted it. When there is no sufficient source, it says that it is a general explanation or a suggested question. It does not present a proposed decision as accepted or an expected result as verified.

### My map

The map stores knowledge points linked to the work: a question, the explanation that was shown, the example, the source, the session, the related decisions and the date. The person can return to exactly the explanation that helped them and ask for a different version without losing the previous one.

Links have meaning: "explains" («explica»), "depends on" («depende de»), "appeared during" («apareció durante»), "helped decide" («ayudó a decidir») or "was applied in" («se aplicó en»). When a concept reappears, it is linked to the existing point; another copy is not created automatically. By default, only the current branch is shown. Other branches are retrieved through search and progressive navigation.

A point can be **explored**, **understood according to the person** or **marked for review**. The system does not infer mastery from it having been opened. When "Mark for review" («Marcar para repasar») is used, the node gets a small visible marker and the header shows how many there are. The mark persists while navigating and can be removed. A possible evolution would be to allow adding a note with the reason and scheduling voluntary reviews.

There are general concepts and explanations applied to a specific version of the project. If the project changes, the application can flag that an applied explanation needs review, keeping its previous version. It must not modify history silently.

### Decisions and clarifications to the worker

When a worker asks for a relevant choice, the decision card shows in everyday language: what it is requesting, what alternatives there are, why it is coming up now, what changes if each one is chosen and what will remain pending. If a requirement comes from the project's instructions, it says so; if it comes from the agent's preference, it says that too.

The person can explore questions without interrupting the worker. If they decide to intervene, Tramora prepares a readable message to review before sending it. Afterwards it would distinguish three milestones: **sent**, **received or acknowledged** and **reflected in observable changes**. A message accepted by an interface does not prove that the code has changed.

## Complete usage example

In a fictional session about payment retries, the builder proposes an "idempotency key" («clave de idempotencia»). The person presses "What does it mean?" («¿Qué significa?») and gets a brief explanation: repeating a request must not produce a second charge. They can open an example and then dig deeper into concurrent requests. Those questions add branches to the map. The reviewer raises what to do if the same key arrives with a different amount; Tramora marks this as an open decision and allows a clarification to be drafted. Days later, the person returns to the node and retrieves the original explanation and the reviewer's message.

That example serves to understand the interface. It does not describe a real integration or an implemented product feature.

## Experience quality requirements

The interface must work with a keyboard and on small screens. The avatar's color and shape can help recognize agents, but name and status always remain in text. The review marker has an accessible label. The view must be able to reduce visual motion. The states "unknown" («desconocido»), "no message available" («sin mensaje disponible») and "no answer yet" («todavía sin respuesta») are legitimate. The person must never have to guess whether they are looking at a fact, a summary or an example.
